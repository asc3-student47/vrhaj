Why: The rubric explicitly requires that "Outputs conform to the Pydantic models defined in the spec." This is the most critical principle. Free-form text is unreliable and difficult for other systems to work with.

How: Define every output your agent can produce as a pydantic.BaseModel. This ensures every output is structured, typed, and validated automatically.

Include Rationale and Evidence with Decisions

Why: The rubric requires the "Final decision (approve / deny / escalate...) includes supporting rationale tied to evidence." Your agent can't just provide an answer; it must explain why it reached that conclusion.

How: Your Pydantic output schema must contain distinct fields for the decision itself (e.g., an Enum), the rationale (a string explaining the reasoning), and the evidence (e.g., a list of source data or facts used).

Use Precise and Appropriate Data Types

Why: Using the correct data types (e.g., float for prices, int for counts) enables automatic validation and prevents the agent from returning text where a number is expected.

How:

Use str, int, float, bool for basic data.

Use Enum to constrain a field to a set of predefined choices (e.g., Sentiment.POSITIVE). This is far more reliable than using a free-form string.

Use list[T] for collections of a specific type.

Nest Pydantic models to represent complex, hierarchical data.

Embrace Minimalism and Optionality

Why: To prevent the agent from fabricating information, schemas should only include necessary fields and explicitly handle uncertainty.

How:

Include Only What's Needed: Your output model should only contain the fields required for the downstream task. Avoid adding superfluous data.

Use Optional for Uncertainty: If a piece of information may not be present in the source data, define its field as Optional[str] = None. This prevents the LLM from inventing a value when one doesn't exist.

Enforce Business Rules with Validators

Why: A valid structure doesn't always mean the data is valid for your business context. Validators enforce domain-specific rules.

How:

Use Field for Constraints: Apply built-in constraints directly in your schema, such as rating: int = Field(ge=1, le=5) to ensure a value is within a specific range.

Use @field_validator for Custom Logic: Implement custom validator functions for complex rules that Field cannot handle, such as ensuring a list is not empty or that a string matches a specific format.

Plan for Multiple Output Formats with Unions

Why: Sometimes an agent needs to return different shapes depending on the situation (e.g., a short answer vs. a detailed report). A typed Union allows this flexibility without sacrificing type safety.

How: Define your agent’s output_type as a union of multiple Pydantic models, such as output_type=Union[ShortAnswer, DetailedReport]. This lets the agent decide which format is most appropriate while still guaranteeing a valid, predictable structure.
